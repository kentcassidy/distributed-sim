MVP Scope — Thirteen Days to Sep 13

Authoritative near-term plan · Sep 1–13, 2026 · rescopes the four-week vision to the real deadline

Ship one thing, complete: a working HLA federation, in C++, where two aircraft each own their own physics, one holds formation on its ghost of the other, and the result is shown to be invariant to how the work is split across federates at zero impairment — then to degrade predictably as network delay rises. A running federation with a real V&V result and a clean, documented repo. Nothing more, on time, beats anything more, late.

The general goal — and the MVP’s place in it A configurable set of N aircraft, each with its own parameters and role in a formation graph, is simulated by a federation whose entities can be partitioned across any number of federates/containers by config alone. The validity claim is partition invariance: for a fixed seeded scenario the aggregate outcome is invariant to how entities are distributed — bit-exact on one host, tight-tolerance across hosts — and degrades predictably as impairment enters the loop. The model may be stochastic (seeded, per-entity turbulence) while each run stays reproducible. The MVP proves this with two aircraft, one host, turbulence off; the general case follows by configuration, not rewrite. (ADR-0013.)

What carries the argument

A prior review doubted two things: C++ depth and distributed-simulation experience. Every hour goes to the smallest artifact that rebuts both — a federation that runs, in C++, and produces a result with a number on it. The result is partition invariance; the legibility is the repo. Those two are load-bearing. Everything else waits.

The V&V Spine: Partition Invariance

The MVP’s validity claim is that the answer must not depend on how the work is divided across federates. It is the federation analog of numerical reproducibility, and it validates the distribution itself — not just the physics. It replaces the four-week vision’s distribution-drift spine (Experiments tab), which needs the cut ensemble; partition invariance needs only the federation you were already building, run twice and compared.

Same scenario, same physics, two ways of splitting the work. The comparison is the V&V.

The two claims, in order

  1. Invariance (the validation). Run the identical deterministic scenario with both aircraft co-located on one federate, then split one to each. At zero injected delay and zero DR error, the aggregate trajectories must match within a tight tolerance. A match proves the distribution added nothing — the federated answer equals the single-machine answer.
  2. Controlled breakdown (the result). Now sweep injected delay in the split case. The follower’s station-keeping degrades while the co-located case stays put. The gap between them, plotted against delay, is the measured cost of putting the network inside the control loop — cross-checked against the analytical delay-margin prediction.
Requirement, generality, and the honest caveats Reproducibility first. Invariance is only checkable if a run replays identically, so the MVP uses conservative time management and turbulence off — a fully deterministic run compared near bit-for-bit. (Post-MVP, per-entity seeded RNG streams restore turbulence while keeping invariance: each aircraft draws the same noise regardless of which federate hosts it.) The unit is the entity. With strict ownership the divisible unit is one aircraft, so a partition is an assignment aircraft → federate → container. Two aircraft give “co-located vs split”; N aircraft over K containers generalize it to invariance across every partitioning — a stronger claim, driven by config alone, and the reason the core is built entity-agnostic (owns a list, partition by config) now rather than later. Determinism has a scope. Bit-exact invariance is realistic for K containers on one host from the same image; across heterogeneous hosts, floating-point ordering makes the honest claim tight-tolerance, not bit-exact. (ADR-0013.)

Project Statement

A shared worldspace holds a large storm — a structured wind field — that stochastically perturbs a configurable set of aircraft (two by default, N by config) flying a coupled formation. Each aircraft is owned and integrated by its own federate; the only thing on the wire is entity state. The same validated physics runs in two modes: a fast single-process ensemble of many randomized scenarios, and a distributed federation of one scenario at a time with real network impairment. The deliverable is a statistical comparison — does distributing the simulation change the distribution of outcomes? — with the run set replayable in real time if wanted.

Reading that statement clause by clause

“A storm that stochastically perturbs the aircraft.” A spatially-structured wind field (a vortex) supplies deterministic forcing that all aircraft feel coherently; a turbulence model supplies the per-run randomness (per-entity seeded streams, so each aircraft's noise is independent of its federate — ADR-0013). Wind enters the flight model at exactly one point — it is subtracted from inertial velocity before the aerodynamics are computed.

“A coupled formation.” In the two-aircraft base case the follower holds station on its dead-reckoned copy of the lead; with N aircraft this generalizes to a formation graph — each follower holds station on the dead-reckoned ghost of its assigned target (a trail chain, a leader-star, whatever the config declares). This coupling is what makes the network measurable: delay and extrapolation error enter a closed physical loop and come out as station-keeping error.

“Each aircraft owned and integrated by its own federate.” Entity ownership, the central rule — its own section below. Nobody computes anyone else's physics.

“The same validated physics in two modes.” One model core, two drivers. A batch driver runs hundreds of randomized scenarios in one process for the statistics; a federation driver runs single scenarios distributed, with time management and impairment. This split is the project's central architectural idea and the thing that makes both the ensemble and the distributed demonstration possible.

“Does distributing the simulation change the distribution of outcomes?” The headline result. Run the ensemble monolithically for a baseline distribution; run a subset federated under latency and dead-reckoning error; compare the distributions, not individual paths. This is the question distributed-simulation programs genuinely worry about — whether a federated execution is still valid for the analysis it is used for — answered with data.

Terminology, stated once and kept straight The ensemble is Monte Carlo: known inputs, random perturbations drawn per run, outputs collected into a distribution — forward uncertainty propagation. It is not MCMC. MCMC is the inverse problem — sampling a posterior over unknown parameters from observed data — and it appears only in the optional storm-identification extension on the horizon. Naming the ensemble “MCMC” would be the one error a technical reviewer would catch.
Stochastic model, reproducible run — not a contradiction “Stochastically perturbs” describes the model’s forcing, not the repeatability of a run. The turbulence is drawn from a seeded generator, so a given seed replays an identical trajectory: the model is stochastic, yet each run is reproducible. Monte Carlo varies the seed across runs to build a distribution; partition invariance (Scope tab) fixes the seed and varies only how entities are split across federates. Reproducibility is the property; invariance is the stronger claim built on it. (ADR-0013.)

Entity Ownership

Every federate is authoritative for its own aircraft and nothing else. It integrates its own equations of motion and publishes the result; it never computes the other aircraft's physics. What it holds for the other aircraft is a ghost — a local, read-only copy, corrected when an update arrives and extrapolated in between.

Why this is the right instinct Localizing each side's calculations is the standard, not a simplification. DIS and HLA federations, and JSE above them, are built exactly this way. Ownership pushes computation to where the state lives and puts only the minimum on the wire, which is precisely why dead reckoning exists and why the federation scales past two entities without changing any existing federate.

Aerodynamics Is a Table, Not a Solve

There is no computational fluid dynamics here, and none in real flight simulators either. Aerodynamics is reduced offline to coefficients — functions of angle of attack, sideslip, Mach, and control deflection — and looked up at runtime. Each step: compute flow state, look up coefficients, multiply out to forces and moments, add gravity, thrust, and wind, integrate one step. The entire flight model is a table lookup and an integration.

Fidelity floor The minimum model is the linearized longitudinal case: four states, constant derivatives, no interpolation. Its eigenvalues are the published short-period and phugoid modes, so verification is a closed-form comparison. Fidelity chosen for verifiability is test-engineer reasoning, not a shortcut. (ADR-0005.)

The Central Idea: One Core, Many Drivers

Two execution needs pull in opposite directions. Monte Carlo wants hundreds of fast, independent runs in one process. The distributed demonstration wants coordinated multi-process execution with time management and impairment. Standing up hundreds of HLA federations for the ensemble would be slow and miserable. The resolution is to build the physics once, cleanly, and wrap it differently for each need. (ADR-0006.)

Same physics, three wrappers. The batch and federation drivers are the four-week deliverables; replay is a horizon item that reuses the federation driver's pacing. The rule that makes it work: the core has no clock and no RTI dependency. Pacing and transport belong to the drivers, never the physics. Any timing assumption that leaks into the core is a defect to correct, not accommodate.

Federation Topology

Three processes, no direct links; every exchange goes through the RTI. In the federated experiment the federates run in separate containers and tc netem shapes the links to inject latency, jitter, and loss at the network layer — real impairment, not a delay variable inside the code. (ADR-0008.)

The logger records both the received ghost and, on a debug channel the control loop cannot see, the owner's truth — so the analysis can measure ghost error directly. It is constrained but not regulating, the standard pattern for a recorder that must never block the federation.

The Storm

A Rankine vortex: tangential wind rising linearly inside a core radius, falling as 1/r outside, plus an updraft term — a closed-form, two-parameter field that both aircraft feel coherently because they share the worldspace. Dryden turbulence (band-limited noise through the standard shaping filters) adds the per-run stochastic component that makes each ensemble member distinct. Wind couples into the flight model at one point: it is subtracted from inertial velocity before angle of attack, sideslip, and dynamic pressure are computed. (ADR-0010.)

Double duty The vortex parameters — center, core radius, circulation — are exactly the unknowns the optional horizon-stage MCMC inversion would infer from a noisy observed trajectory. The same storm model serves both the forward ensemble and the inverse problem.

Time Management

Each federate has two independent switches. Regulating: my timestamped messages make others wait for me. Constrained: I wait for others. Both ships are both; the logger is constrained only. A federate calls timeAdvanceRequest(t), the RTI delivers all messages at or before t in order and then grants the advance, and only then does the federate step. Lookahead is the promise not to send anything earlier than now + L; larger means more parallelism, and zero — with everyone regulating and constrained — deadlocks.

Interview-relevant, and a deliverable Inducing the zero-lookahead deadlock deliberately and writing up the resolution is a milestone item. Being able to explain why it deadlocks, without notes, is the highest-value single thing on this tab. Note also that this conservative scheme is exactly what a human-in-the-loop (virtual) federate could not obey — see LVC on the Reference tab.

Dead Reckoning

Both sides run the same cheap extrapolation of the ghost between updates. Crucially, the sender runs that identical model against its own truth and publishes a fresh update only when the divergence exceeds a threshold. That sender-side mirror is what turns fixed-rate publishing into send-on-need, and it is the part people miss. Two algorithms are implemented — constant velocity and constant acceleration — and compared.

The Headline Result

Does distributing the simulation change the answer? Build a baseline outcome distribution from the monolithic ensemble, then run a subset federated under real network impairment, and compare the distributions — not individual trajectories, which never match, but their statistics. Report how far the federated distribution drifts from the monolithic one as latency and dead-reckoning error rise.

This is the question a distributed-simulation program actually worries about: whether a federated execution is still valid for the analysis it is being used for. Answering it with a measured distribution drift is a validation result, not a demo.

The Ensemble (Monte Carlo)

The batch driver runs many scenarios over the same nominal setup, drawing per-run randomness: turbulence seed, initial-condition scatter, and storm-parameter jitter. Each run yields an outcome metric — peak or RMS station-keeping error, say. The collection is a distribution, reported with confidence intervals rather than a single number. Hundreds to thousands of runs complete in minutes in one C++ process across cores.

This is the not-a-videogame part A game produces one plausible trajectory. This produces a distribution with intervals and a coverage story. Let the artifact make the point; do not make the comparison out loud.

The Coupling That Makes the Network Measurable

The follower's formation law consumes the dead-reckoned ghost of the lead, never its truth. So network delay and extrapolation error enter a closed physical loop and emerge as station-keeping error. As a secondary, analytical check, the critical delay at which the loop loses stability can be predicted from the tracking law's phase margin and crossover frequency — committed before the sweep — and compared to the measured value.

Optional Horizon Extension: MCMC Storm Identification

After the four weeks, and only then: given one noisy observed trajectory, infer the storm's parameters — vortex center, core radius, circulation — by sampling the posterior with Metropolis-Hastings, each proposal costing one forward integration of the model core. Because the true parameters are known (they were set), posterior coverage can be checked. Then ask how much the posterior widens when the observation is a dead-reckoned ghost rather than truth — turning network degradation into a quantified loss of inferential precision. This is the genuine, correctly-named MCMC; three to five days, gated behind everything above.

Monte Carlo vs MCMC

Monte Carlo — in scope

Known inputs, random perturbations drawn per run, outputs collected into a distribution. Forward uncertainty propagation. This is the ensemble. No chain, nothing inferred.

MCMC — horizon only

Sampling a posterior over unknown parameters given observed data. An inverse problem. Appears only in the optional storm-identification extension. Calling the ensemble “MCMC” is the one naming error a reviewer would catch.

LVC: What This Engine Can and Cannot Do

Constructive — built

Simulated entities, no human in the loop during execution. Both drivers (batch and federated) are constructive. Deterministic given a seed, which is what makes the ensemble possible.

Virtual — accommodated

Real human, simulated aircraft. Not built in the month. Reachable via the driver split, but requires heterogeneous time management (a free-running, best-effort federate) and gives up ensemble reproducibility. (ADR-0011.)

Live — not supported

Real people, real systems. Would enter only through a DIS/TENA gateway federate bridging range instrumentation. Horizon item; the one that maps most directly onto range operations.

Batch versus federated is an execution-mode distinction, not an LVC one — both are constructive. The reason virtual is not a config flag is time management: a human cannot be held at a time advance request, so a virtual federate runs best-effort and wall-clock-paced, which breaks the conservative scheme and the determinism the ensemble depends on. The replay driver is structurally a virtual federate minus the input device, which is why building replay also builds the pacing path a virtual mode would need.

Glossary

HLA
High Level Architecture, IEEE 1516. Federates exchange FOM-described data through an RTI.
Federate / Federation
One simulator process / the set of them running together.
RTI
Run-Time Infrastructure. Middleware for pub/sub routing, time management, object lifecycle.
FOM / SOM
Federation Object Model / the subset one federate publishes or subscribes to.
Ownership
Exactly one federate is authoritative for each attribute of each object instance.
Ghost
A local read-only copy of a remotely owned entity, corrected on update, extrapolated between.
Dead reckoning
Extrapolating a ghost between updates; the owner publishes only when its own copy of that extrapolation exceeds an error threshold.
Regulating / Constrained
This federate's timestamps constrain others / this federate waits for others.
Lookahead / LBTS
The minimum future offset a regulating federate promises / the lower bound on timestamps the RTI computes to decide a safe advance.
Rankine vortex
A two-parameter wind field: linear inside a core radius, 1/r outside.
Dryden turbulence
Band-limited noise through standard shaping filters; the stochastic forcing.
netem
Linux tc queueing discipline that adds latency, jitter, and loss to an interface — real network impairment.
DIS / PDU
IEEE 1278, the older broadcast standard / one of its messages.
TENA
Test and Training Enabling Architecture; range instrumentation, live-asset oriented.
LVC
Live, Virtual, Constructive — a taxonomy by who and what is real.
JSE
Joint Simulation Environment; the programme-level context.

The batch ensemble driver is not containerized or virtualized — it is one multi-threaded process. Only the federated driver touches containers and VMs.

MVP deployment & toolchain (ADR-0012) Base image is Ubuntu 22.04 + GCC 11 — glibc, the platform Portico is tested against (ADR-0001), used identically for dev, CI, and the experiment. Not Alpine: its musl libc fights Portico’s glibc/JVM binaries for no benefit here. Toolchain: build-essential, cmake, and Portico wired through CMake — Portico bundles its own JRE (Java 8), so no system JDK is installed. For the MVP, development is localhost / WSL2 and latency is an in-federate delay buffer; a single build/dev container gives reproducibility, and the multi-container tc netem harness (needs iproute2 and NET_ADMIN) is post-9/13. Edit in VS Code + WSL2 / Dev Containers so the dev environment equals CI equals the experiment.

Standards and Background

  • IEEE 1516 — HLA framework, interface spec, object model template.
  • IEEE 1278 — DIS, including the dead-reckoning algorithm set.
  • Military turbulence handbooks — the Dryden model specification.
  • DoD VV&A doctrine — the structure the V&V report follows.
  • Flight dynamics texts — stability derivatives, linearized models, published mode characteristics.
