WHAT WAS BUILT (the constructive core, in order)
------------------------------------------------
1. Scenario + Partition (RTI-free, in dff_core):
   - Scenario.hpp/.cpp: CSV loader (id-sorted, loud-failing) -> vector<EntitySpec>
     (id + initial State). scenarios/two_aircraft.csv.
   - Partition.hpp/.cpp: tileVolume() splits the world AABB into K equal slabs along an
     axis; slabOf() assigns a point to a slab via a UNIFORM HALF-OPEN rule ([min,max) on
     every axis, -1 if outside); assignEntities() maps each entity -> slab. Determinism
     starts here (sort by id; disjoint tiling; loud config errors).
   - Format decided with the user: CSV (not JSON/YAML); multi-file if sections ever needed.

2. Control plane over the RTI (FOM interactions in foms/dff-fom.fed; encoded via
   src/federate/Encoding.*, since .fed carries no datatypes):
   - Enroll{FederateName}            fed -> controller
   - AssignEntity{TargetFederate, EntityId, Position, Velocity, Orientation, AngularV}
                                     controller -> fed  (full state)
   - AssignSector{TargetFederate, SectorId, Min, Max}   controller -> fed
   - StartRun{Dt, WorldMin, WorldMax}                   controller -> all
   - Shutdown                                            controller -> all
   Encoding gained encodeQuat/encodeDouble/encodeUint32/encodeString (+ decoders).

3. Controller = federation manager (src/controller/), promoted from stub to a real
   federate. It is the SOLE CREATOR of the federation and the coordinator:
   create -> join -> subscribe Enroll / publish the rest -> collect roster (live pump +
   non-blocking ENTER via select) -> on ENTER: K = roster size, loadScenario, tileVolume,
   assignEntities, send AssignSector per federate + AssignEntity per entity, broadcast
   StartRun, write sim_out/controller.ndjson (world + sectors + owners, meta-only) -> hold
   (keep pumping) until a 2nd ENTER -> broadcast Shutdown -> destroy.
   K is chosen dynamically = number of federates that enrolled before start.

4. Aircraft federate (src/federate/) reworked: JOIN-ONLY (controller creates), enrolls,
   waits for StartRun, then builds EXACTLY the aircraft the controller assigned it (dropping
   the old name-derived single aircraft), integrates all owned, publishes, and logs NDJSON.

5. NDJSON evolved: per-federate meta line (federate, dt, sectors) + per-frame
   {"t","wt","aircraft":[{id, role:"owned", pos, vel, quat}]}. wt = wall-clock microseconds
   (system_clock), METADATA ONLY -- it lets the diff show that the same LOGICAL step was
   computed at different REAL times/interleavings while the truth stayed identical. Truth is
   written at setprecision(17) so the decimal round-trips to the exact bits (required for a
   bit-exact check, not just ~9 digits). t=0 is the initial state; frame t=i*dt is the
   post-advance state at step i (off-by-one label fixed).

6. dff_diff (src/diff/, standalone C++17, no RTI): the V&V tool. Takes N run directories,
   parses per-federate NDJSON, keys truth by (entity id, logical step), and compares every
   run bit-exactly against the first. Reports type-specific verdicts: VALUE DIVERGENCE
   (shared point computed to different bits), COVERAGE MISMATCH (a point present in one run
   only), NO OVERLAP. Exit 0 iff invariance holds -- CI-friendly. Also narrates the
   EXECUTION divergence the invariance holds across (which federate owned each id; wall-clock
   spread among federates at a step).

THE RESULT (verified with the user)
-----------------------------------
- K=1 (one federate owns both aircraft) vs K=2 (one each): dff_diff reported
  "PARTITION INVARIANCE HOLDS (bit-exact)" -- 200/200 points identical, 0 divergent,
  0 coverage gaps. Ownership differed (entity 2: fedsolo in K=1, fed2 in K=2) and the
  federates ran ~4 ms apart in wall-clock at a shared step -- yet the truth was bit-identical.
- Falsification check: the user deleted one NDJSON line at random; the tool correctly flipped
  to FAILS (coverage mismatch, "only in K1: 1"). A V&V tool that never fails isn't trustworthy;
  this one fails when it should.
- K=3 explored: with 2 aircraft and 3 slabs, one federate correctly owns an IDLE slab
  (aircraft at y=500,1000 fall to the upper slab of each seam under the half-open rule, so
  slab 0 is empty). Correct spatial behavior, not a bug.

WHY IT HOLDS
------------
Aircraft are INDEPENDENT in the constructive core (collision::resolveWorld is a no-op), so
each aircraft's truth is a pure function of (its IC, dt, model, integration order). Identical
ICs (disseminated from one scenario), identical dt (StartRun), same host/image FP, and
precision-17 round-trip => bit-identical regardless of which federate computes it or in what
real-time order. Invariance lives in the CONSOLIDATED, truth-keyed data, not in federate-level
execution.

KEY DECISIONS / FIXES ALONG THE WAY
-----------------------------------
- Controller as SOLE CREATOR (resolves a nasty class of Portico startup bugs): simultaneous
  createFederationExecution calls raced -> either a mid-creation NullPointerException on join,
  or a SPLIT-BRAIN (each federate created its own isolated "DffFederation", no reflections).
  Fix: only the controller creates; aircraft federates are join-only with bounded retry.
- Controller must KEEP PUMPING callbacks while waiting (non-blocking ENTER via select),
  otherwise as coordinator it goes unresponsive and other federates' resign times out. This
  also gives live enrollment printing and clean, coordinated teardown.
- Enroll must let declaration management SETTLE (pump a few callbacks after publish, before
  send) or the interaction is routed to nobody (subscription not yet known) and silently lost.
- World corridor shortened from X=20000 to X=2500 (planes only travel ~2000).
- Removed the vestigial "wait"/interactive ENTER-barrier plumbing (superseded by StartRun).
