  Method A is more realistic for our design, and it's not close — precisely because you've chosen static, globally-broadcast boundaries. The deciding factor is: the partition map is deterministic and known to everyone.

  - With Method A, the releasing owner runs slabOf(pos) against the shared world bounds and gets exactly one destination federate. No round-trip, no ambiguity.
  - Method B (broadcast "who can own this?" → volunteers) only earns its cost when the map isn't globally known, or is dynamic, or ownership is contended — because then you genuinely have to ask. In our case every federate would compute the
    identical answer to that broadcast question, so the auction is pure chatter plus a tie-break you don't need. You'd also have to handle "two volunteers" and "zero volunteers" races that Method A makes impossible.

At the physical network level, implementing DDM by simply using mapping tables of IP addresses to federates is generally not scalable, because the central RTI component would become a massive bottleneck.Instead, modern RTIs (Run-Time Infrastructures) physically map DDM regions and grid cells directly to IP Multicast groups or utilize specialized publish-subscribe network topologies.Here is exactly how DDM is implemented at the low network level:1. The Multicast Group Mapping ApproachThe most common way to offload DDM matching from the CPU to the actual network hardware (like switches and routers) is through IP Multicast.Grid/Region to Multicast IP: The simulation space is divided into discrete zones (or grid cells). Each zone is assigned a specific IP Multicast address (e.g., 224.1.2.3).Subscribing = Joining a Group: When a federate creates a subscription region that covers a specific grid cell, its computer sends an IGMP Join message to the network switch. This tells the network hardware, "I want to receive data sent to this multicast IP."Publishing = Sending to a Group: When a federate updates an object in that grid cell, it sends a single UDP packet to that specific multicast IP.Hardware Routing: The physical network switches look at the multicast destination IP and clone the packet only to the specific physical ports where subscribing federates are plugged in. The RTI software doesn't have to manually route the data.2. The Hybrid Connection-Oriented Approach (TCP/UDP Mix)Because IP Multicast can be unreliable (UDP-based) and difficult to configure across different corporate or military networks, many modern commercial RTIs use a hybrid peer-to-peer / connection-oriented topology:Control Plane (TCP): A central RTI executive (or a distributed set of forwarders) maintains the exact state tables of who is listening to what.Data Plane (UDP/TCP Peer-to-Peer): When a federate's region changes, the control plane sends a lightweight mapping update to the relevant federates. If Federate A needs to send data to Federate B, they establish a direct peer-to-peer network socket.Dynamic Connection Tables: The RTI software maintains a dynamic matrix of connections. If an intersection between two federates' regions ends, the RTI closes or silences that specific peer-to-peer network pipe to save bandwidth.Why Simple IP-to-Federate Tables FailIf the RTI only used a flat table of IP addresses, it would have to use one of two inefficient methods:Broadcast everything to all IPs and let the receiving computer throw away what it doesn't need (wastes massive network bandwidth).Have a central server process every single data update, look up the table, and manually forward the packet to the correct IPs (creates a massive CPU and network bottleneck at the server).By using IP Multicast or dynamic peer-to-peer routing, DDM successfully pushes the filtering logic down to the network layer.
